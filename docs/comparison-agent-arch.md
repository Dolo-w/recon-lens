# 与《通用 Agent 平台技术架构》文档的对照

对照三方：文档的设计主张 / recon-lens 的实际实现 / 我先前给的九层标准框架。

## 一句话

**骨架高度一致，取舍系统性分叉。** 文档是「通用平台」的架构（多业务、多租户、水平扩展、模型与向量是标配）；
recon-lens 是「垂直对账业务」的 Agent（单实例、单租户、确定性优先、模型与向量都是可关的增强）。
两者在同一张分层图上几乎能一一对上，但每条线的默认值相反——所以不能照抄，只能挑着吸收。

## 三方定位

| | 文档 | recon-lens | 我给的标准框架 |
|---|---|---|---|
| 目标 | 通用对话式 Agent 平台 | 对账业务的可对话 Agent | 「一个 agent 该有哪些部分」的对照尺 |
| 部署 | 多实例 + Redis + 向量库 | 单实例单租户（架构文档自述边界） | 不论部署，按层拆 |
| 模型地位 | 主力（意图、指代、工具选择都靠它） | 增强项，可整体关闭降级到词表/模板 | 无状态推理核，可替换 |
| 正确性来源 | 语义相似度 + 提示词约束 | 业务键 + 三道闸门 + 人批 | 护栏层 |
| 成本 | 通篇未提 | 五桶预算 + 熔断 + 快路径 | 上下文管理 |

## 逐维度对照

| 维度 | 文档主张 | 我们的实现 | 判定 |
|---|---|---|---|
| 分层 | 6 层 + 2 支撑 | 包结构与之同构 | 一致 |
| 会话记忆 | Redis，近 3–5 轮，TTL 24h | MySQL 全轮 + 8000 窗口滚动摘要（55% 触发）+ 结论板 | 我们更可回放；文档更省事 |
| 长期记忆 | 向量库语义召回，相似度 >0.75 才注入 | 四分类：SQL 精确 / 键匹配 / 元数据过滤 / 向量仅自由文本 | **我们更对**（见分叉 1） |
| 检索 | 向量 + BM25 混合，TopN=5，阈值过滤 | 三层降级（向量/全文/关键词），层内 min-max 归一 + 层间权重 | 我们更细；我们缺「绝对阈值」 |
| 意图识别 | 大模型分类 + 槽位 + 指代消解，≤200ms | 词表 + 模型双路，12 字快路径，熔断 3 次/5 分钟，冲突列选项 | 我们更稳；200ms 是乐观值 |
| 工具 | 按需加载，单次 ≤10 个 | 18 个全量注册，但**模型不直出 tool_calls** | 架构不同，收益不同（见分叉 3） |
| 沙箱 | 工具沙箱执行 | 无沙箱：表白名单 + 只读探针 + 禁多语句 + 分片键约束 | 威胁模型不同，但该写成显式边界 |
| 治理 | 前三段（鉴权/限流/敏感词）+ 中（权限/超时/熔断）+ 后（审核/脱敏/二次确认） | 三道闸门 + confirmationCode 内容哈希 + MCP 不直通 + 输出脱敏 | **我们更硬**；我们缺限流与敏感词 |
| 降级 | 模型 300ms 超时降级规则，重试 2 次 | 分层熔断（路由/归因/起草各自实例）+ 冷却 5 分钟 | 各有取舍；**LLM 调用无重试**是我们的缺 |
| 流式 | 流式输出，首字节 ≤1s | SSE 分事件（plan/intent/tool/delta/done） | 我们粒度更细 |
| 评估 | 四个「≥90%/85%/90%/99.9%」目标 | step 轨迹 + 16 项 smoke + golden-set + 每批 A/B 实测 | 文档给指标，我们给测法，该合起来 |
| 成本/预算 | **无此章节** | TurnBudget 五桶 + 砍序 + token 口径统一 | **文档硬伤** |
| 多轮指代 | 模型语义消解 | 槽位继承 + resumePending + 结论板 + 「第 N 条」草稿引用 | 我们可解释、可回放 |

## 四处系统性分叉

**1. 记忆的落点：向量库 vs 业务表**
文档把「长期记忆」默认放进向量库、按相似度召回。对通用助手成立，对账业务不成立：
「这一版规则为什么这么写」「上次这类差异谁批的」本质是**主键查询**，不是相似度搜索。
我们 D3 的四分类已经回答了这个问题（结构化事实走 SQL、归因结论走键匹配、案例走元数据过滤、
只有自由文本用向量）。文档的 >0.75 阈值可以借鉴到 `DocChunk` 侧，但**不该借到记忆侧**。

**2. 中间件的假设：Redis/向量库是标配 vs 不引入新中间件**
文档的缓存、分布式锁、会话都压在 Redis 上；我们 ADR-D6 明确不引入，槽位并发用 MySQL 乐观锁
（state_rev + 3 次重试，批 4 实测 4 轮×2 并发无丢更新）。差别只在**部署形态**：
单实例下乐观锁够用；要上多实例，第一个该加的是「会话级分布式锁」，而不是向量库。

**3. 模型在链路里的位置**
文档假设模型**直出工具调用**（所以「按需加载工具、单次≤10」才有意义）。
我们的模型只输出 `ChatPlan`（动作 + 槽位 + 证据），动作由代码分派——工具 schema 从不进 prompt，
只有 15 个动作名进系统提示。所以「工具按需加载」在我们这里收益很小；
反过来，文档那套形态下「模型选错工具」是一类我们**结构性没有**的故障。

**4. 正确性的来源：语义阈值 vs 业务键**
文档靠「相似度阈值 + 提示词约束」保证正确；我们靠「业务键匹配 + 闸门校验 + 人批」。
前者在开放域是唯一解，后者在闭域是更便宜也更可审计的解。文档未讨论「相似度 0.8 所以可以执行」
这种判断在业务上是否站得住——这正是我们闸门存在的理由。

## 文档里该吸收的（按优先级）

1. **SLO 基线**：四个准确率指标落进批 5 的评测报告，与 golden-set 输出字段对齐（意图准确率 / 多轮完成率 /
   检索命中率 / 工具失败率）。我们现在只有「跑绿了」，没有「对了多少」。
2. **限流**：我们只有 API key 与每会话预算，没有 QPS 级限流。单实例也该有，否则一次脚本刷接口就打死引擎。
3. **LLM 调用重试 + 幂等**：现在 transient 失败直接计入熔断计数，一次网络抖动就浪费一格（3 格就熔 5 分钟）。
   建议重试 1 次（只对 5xx/连接超时），仍失败才计数。
4. **绝对阈值**：我们的融合分只有相对序，没有「低于 X 就不给」的闸。小语料下 min-max 会把中间那篇抬上来
   （批 4 实测靠标题 +10 才没沉底）。
5. **敏感词与内容审核**：`Masking` 只管数据脱敏，不管输出审核。
6. **Redis**：只在真上多实例时考虑。**不建议**为了「符合架构文档」提前引入。

## 我们有而文档没写的

- **闸门分层与审批绑定**：`confirmationCode` + 内容哈希，聊天里说「批准」不算数。
- **闸门写在工具实现里**，不写在编排层——换 runtime 也绕不过（ADR-D1 硬约束）。
- **三档降级**：P0 无模型也能跑全流程，能力随环境单调增。
- **预算账本**：五桶 + 砍序 + 统一 token 估算口径（文档通篇最大的空白）。

## 文档自身的三处硬伤

1. **成本章节缺失**：14 个章节没有一个字讲 token 花多少、哪里该熔断、预算怎么分。通用平台最容易被打穿的不是延迟，是账单。
2. **300ms 模型超时**：对 DeepSeek 这类服务首次响应常在 1s 以上的，300ms 等于常态降级；建议 800–1500ms。
3. **「重试 2 次」未定义幂等键**：写类工具重试会重复执行。我们靠 `confirmationCode` + 分片先删后写解决，
   文档没有对应机制。

## 对 6 批计划的影响

- 批 5（观测）正好补文档的评估章节：**它给指标，我们给测法**。建议 M17 的输出字段直接对齐那四个指标。
- 新增一条候选（不进本批）：LLM 调用重试 1 次 + 绝对阈值，都是 10 行内的改动，可以挂在批 5 尾巴上。
- 批 6 之后若真要「平台化」：顺序是 限流 → 分布式锁 → 工具按需加载，**不是**先上向量库。

## 结论

对齐的是骨架，分叉的是默认值。文档适合当「通用平台的能力清单」用——照它验收会缺成本与验证方法；
recon-lens 适合当「闭域 Agent 的参考实现」用——照它抄会缺多实例与通用性。
两者合并的正确姿势：**用文档的指标衡量，用我们的闸门保证，用批 5 的评测把两者接起来。**
