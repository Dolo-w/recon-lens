# recon-lens 架构说明 —— 按 Agent 六组件框架讲清楚

> 用途：对外讲清楚 recon-lens 的架构（为什么这么设计、取舍逻辑、业务内容、生产级评估、未来规划）。
> 框架来源：《Agent 架构详解与 recon-lens 对照》（2026-11-11）的六组件框架；内容更新至 2026-11-22（v4 知识层 + 出口层 + 意图路由共识栈补齐之后，commit daf35a1）。
> 阅读对象：CTO / 面试官 / 想评估这套系统的人。所有「生产级」结论都按真实边界写，不吹。

## 一、recon-lens 是什么（业务内容）

**一句话：计费/账单的对账与稽核基础设施**——把两侧账本（比如计费系统的费用明细 vs 结算系统的账单）按业务规则逐键比对，找出每一条差异、归因到具体原因（税率/汇率/口径/漏单/重复计费…），支撑追缴/补发/豁免的闭环处置，最后输出财务可读的报告和争议证据包。

完整业务链路：

```
取数(Lago/Orb API/CSV) → 归一化导入(不可变快照) → 规则对账(Java+Go 确定性引擎)
  → 差异集(分类/方向/金额) → 四层归因(知识库/模式库/LLM/模板) → 闭环台账(核销/豁免/审批)
  → 出口(REST / MCP 24 工具 / 财务 HTML 报告 / 证据包 CSV / ROI 报表)
```

典型场景：AI 公司的 token 计量计费对账（模型调用量 × 价格表 = 应收，和账单系统实收对平）、SaaS 订阅对账、支付渠道对账。差异少收一笔钱就是直接资损——这是「为什么值得做」的商业答案。

**在 agent 架构里的定位**（对照 11-11 文档的原始定位，已演进）：

- 仍然首先是 agent 架构里的「工具与行动」层——确定性对账引擎，MCP/REST 供上层 harness 调用；
- 但已经**不只是被调用的工具**：内部长出了自己的 agent 编排层（四阶段状态机 + 带意图路由的对话入口 + 槽位状态机 + 评估闭环），对齐了业界 agent 共识栈的六个层面。它现在是「自带可对话入口的确定性能力层」。

## 二、六组件逐层：怎么做的、为什么这么选

### 2.1 大模型内核（LLM Core）

**做法**：核心计算层（金额比对、方向派生、汇总）**完全不用 LLM**。LLM 只出现在三个位置：

1. **归因第三层（L2）**：知识库、模式库都覆盖不了时，调模型生成「可能原因假设」——是假设不是结论，要用数据去验；失败安静降级回模板，不让一批差异集体失声。
2. **规则起草**：一句话业务描述 → 规则草稿（仍要过三闸门才能跑生产）。
3. **对话理解**：chat 入口的人话翻译（意图识别主通道）。

**为什么（取舍逻辑）**：铁律「**LLM 绝不算金额**」。LLM 算钱会幻觉、不可复现、不可审计——而对账系统的一切价值都建立在「可复现、可审计」上。所以 LLM 被定位为「解释器/翻译器」，不是「计算器」。这同时是权限最小化：模型永远碰不到真实金额和数据的执行权。

**代价（如实说）**：极端场景（完全没见过的差异形状）下，LLM 归因的质量依赖模型能力；我们用「人工确认回流（K1）+ 模式库热加载（K2）」把这类场景逐步变成 L0/L1 命中，LLM 的使用率随使用时间下降——这正是「越用越准」的机制，ROI 端点（`/api/knowledge/roi`）可以量化验证。

### 2.2 规划与反思（Planning & Reflection）

**做法**：recon 的「规划」不是让 LLM 自主拆任务，而是三条确定性控制流：

- **归因分层定序**：L1 知识库 → L0 模式库 → L2 LLM → L3 模板。顺序即语义：人工确认的证据强于机器联想，免费的永远先于花钱的。
- **规则治理三闸门**：草稿 → 影子试算 → 人工审批（确认码 + 内容哈希，会话里说「批准」不算数）。改规则不直写生产。
- **agent 四阶段状态机**（`AgentOrchestrator`）：感知 → 规划 → 行动 → 沉淀，每步落库、可回放、崩溃恢复（只重放 ACT 之后的事务性动作）。

**为什么（取舍逻辑）**：元原则「**确定性的归代码，不确定的归模型**」。对账是金融场景，流程必须可控、出错要能回退——这正好是 Plan-and-Execute 优于自由 ReAct 的场景。我们的三闸门 = Plan-and-Execute 的「先看到完整计划再动手」；四阶段落库 = 反思与恢复的持久化基座。没有采用自主 ReAct 循环跑业务，因为对账的每一步都必须是可审计的确定性动作。

### 2.3 记忆（Memory）

**做法**：四处，分工清晰：

1. **规则库（版本化）**：规则=数据，改规则落新版本、旧版本保留；每个任务钉死 `rule_version + rule_snapshot`——任何历史任务都能按当时的规则原样回放。
2. **不可变数据快照**：对账结果 = `f(快照A_vN, 快照B_vM, 规则_vK)`。「数据源先说 A 后来说 B」由新快照承接、旧快照永可审计。
3. **归因知识库（v4 大升级）**：按「规则 + 差异类型 + 字段 + 形状签名（含时间桶 `|@YYYY-MM`）」命中复用；**只存形状不存值**（绑业务值命中率恒为 0）；多候选只追加不覆盖（9 月的税和 10 月的手续费不撞键）；信任梯度人工 0.9 > 模型 0.5。
4. **路由层语料**：chat 没听懂的原话落库（`recon_chat_fallback`，append-only），挖掘确认后沉淀进 golden 回归集——记忆不只服务归因，也服务路由的自我进化。

**为什么（取舍逻辑）**：知识库是「结构化版 RAG」——用规则签名代替向量召回，用信任梯度代替重排置信。选精确键匹配不选向量检索，是因为归因键是**可机械构造的**（规则+类型+形状），精确命中零误召回；向量检索留给「说法改写」这类语义模糊场景（意图缓存将来可选升级），两者不混用。时间桶是踩坑后加的：没有它，9 月的因果会被 10 月复用——键过粗导致因果混叠，比没有记忆更危险。

### 2.4 工具与行动（Tools & Actions）

**做法**：三个出口，同源同一套 service：

- **MCP server：24 个工具**（stdio + streamable HTTP），任何支持 MCP 的 agent 零适配接入；
- **REST 全套**（jobs/diffs/prices/lifecycle/rules/reports）；
- **人话对话入口**（chat），背后还是同一套工具。

执行层是 **Go worker**：正式对账全走 Go（最大可提交前缀提交语义、分片并发、断点续跑、事务+失败回滚），Java 负责编排、DSL、归因、出口。

**为什么（取舍逻辑）**：
- MCP 而非每家写适配：一次实现，任意 agent client 都能调——「AI 的 USB-C」，这是标准答案没有悬念。
- Go 做执行而不是 Java 全包：对账热路径要的是**GC 可控 + 低停顿 + 简单并发**（goroutine 分片），Java 编排层保住生态和业务表达力。执行纯化还有个隐性收益：性能问题和业务问题天然分层，互不牵连。
- 工具面按需加载：基础 18 个常驻，写动作（导入/建表/跑批）按需暴露——工具越多模型选得越差（业界实测 200 个工具准确率掉到 64%），我们 24 个还在安全区。

### 2.5 环境与反馈（Environment & Feedback）

**做法**：四条反馈回路，全部有结构化出口：

1. **人类闭环回流（K1）**：RESOLVE/EXEMPT 带 reasonId 自动 teach 进知识库（人工 0.9），best-effort 不挡核销。
2. **审批流**：追缴/补发/规则上线必须人工拍板，审批台账 append-only 留痕。
3. **引擎自检**：排序口径不一致打 WARN、键冲突报 DUPLICATE_KEY、单侧未就绪标 PENDING 不冒充 MISSING——帮人立刻定位「配置错」而非误报「业务漏单」。
4. **评估闭环**：知识层 ROI 报表（四层命中计数 + llmCallsSaved）、路由指标（通道/per-intent/fallback/熔断/缓存命中）、golden 意图回归集（26 条，卡住每次路由改动）、Go worker golden-set 对照（Java/Go 双实现结果一致性）。

**为什么（取舍逻辑）**：agent 评测体系的共识是「没有 eval 数据集 + trace，改一次 prompt 不知道变好还是变坏」。我们把这条共识做成了产品能力：ROI 报表既是内部验收（v4 验收口径「越用越准可量化」），也是对外卖点（给 CTO 看的省钱账）。golden 集合的来源是 fallback 语料挖掘——负样本不收集，路由层就是开环。

### 2.6 编排运行时（Orchestration / Harness）

**做法**：三层编排，各管一段：

1. **对话编排**（chat 层）：快慢双路径（词表 30ms 直出高频意图 / LLM 主通道理解长尾）；模型输出过三道闸（解析层校验 → 证据三态（模型说的规则码/任务号必须在库里真实存在，CONFLICT 直接打回）→ 两段式执行（写动作必须用户点头））；槽位状态机（追问必挂起、一次一问、补答只填参数、15 分钟过期——过期的确认不是确认）；熔断半开、意图缓存、复合意图只读自动跟跑。
2. **任务编排**（AgentOrchestrator 四阶段）：见 2.2。
3. **执行编排**（引擎 + Go worker）：分片、水位、幂等、恢复。

**为什么（取舍逻辑）**：**为什么不用 LangGraph / Spring AI 的编排？** 诚实答案分两半：LangGraph 的三个核心抽象我们其实都自研等价物了——图状态机 = 四阶段状态机；Checkpointer 断点续跑 = 步骤落库 + 崩溃恢复；human-in-the-loop 打断 = 审批闸门。选择自研的原因是①Java 栈里 LangGraph 没有成熟官方实现，Spring AI 当时编排能力薄弱；②我们的流程是**业务定义的确定性流程**，不需要让 LLM 决定控制流，图框架的灵活性对我们是负资产；③状态机 + 事件落库总共几百行，可测试可审计，不引入框架依赖。代价也要认：没有现成的 tracing/时间旅行 UI，回放靠表里的事件自己查。

**多 agent 的明确取舍：不做。** 编排者已存在于外部（任何 MCP client），内部再造多 agent 编排是重复建设；写动作审批链会被两个自治 agent 撕裂；对账没有「需要 agent 间自主协商」的真实场景；批量并发诉求已由 Go worker 分片满足。知道什么时候**不**用某个热门架构，比会用它更重要。

## 三、与业界 agent 共识栈的对照（2026-11 复核）

| 业界共识层 | recon-lens 现状 | 结论 |
|---|---|---|
| 快慢双路径路由 | 词表快路径 + LLM 主通道 + 熔断半开 | ✅ 对齐 |
| 解析层校验（不信 prompt 约束） | 动作枚举/正则/类型全量重校验 | ✅ 对齐 |
| 实体白名单/能力注册表 | **证据三态**：语义级核实（实体须真实存在） | ✅✅ 超业界常见实现 |
| 槽位填充状态机 | 通用 SlotProtocol + 挂起过期 | ✅ 对齐（2026-11-22 补齐） |
| 风险门 / HITL / time-boxed 审批 | 全写动作确认 + 挂起 15 分钟过期 + 审批台账 | ✅ 对齐且更严 |
| 路由评估闭环 | per-intent/通道/fallback 指标 + 语料落库 + 挖掘出口 | ✅ 对齐（2026-11-22 补齐） |
| Golden benchmark 卡改动 | intent-golden 26 条 + Go golden-set 对照 + 1041 测试 | ✅ 对齐 |
| 语义缓存（embedding 版） | 文本精确版 + CANON 归一 | ⚠️ 刻意简单，同义改写不命中 |
| 意图 embedding 召回层 | 未做（~30 意图，规模痛点不存在） | ➖ 判定不适用 |
| 多 agent 编排 | 明确不做 | ➖ 架构决策，见 2.6 |

## 四、生产级能力评估（如实）

**结论先行：架构是生产级的，部署形态是原型的。** 这句话是文档里最重要的一句——面试讲原型 + 对差距的认知，绝不称生产级。

**已经到生产级标准的**：

1. **确定性内核**：BigDecimal 全程、显式键精确配对（无按位配对）、快照/cut-off 水位（PENDING 不冒充 MISSING）、幂等重跑、分片断点续跑、失败回滚——这些是对账的生命线，全部有测试压着。
2. **执行层双实现对照**：Java 与 Go worker 有 golden-set 一致性对照（本机已真跑），执行引擎的行为被两套实现互相钉住。
3. **治理与安全**：规则三闸门、确认码+内容哈希审批、API key 鉴权、审计留痕、PromptGuard 注入定界、公式注入钳制、LLM 权限最小化（不碰金额、不执行）。
4. **可观测与可回放**：四阶段每步落库、崩溃恢复、任务钉死规则快照可原样重放、ROI/路由指标有 HTTP 出口。
5. **降级矩阵 P0/P1/P2 三档**：没 LLM、没价格表都能跑，能力只增不减——LLM 是增强不是依赖。
6. **质量基建**：1041 测试 0 skip、ArchUnit 架构边界、CI（Go vet/race/build）、golden 回归集、迁移脚本全带回滚。

**还不是生产级的（差距如实列）**：

1. **单机部署**：H2/MySQL 单库单实例，没有横向扩展；真正的多租户需要 C/S 化，那是另一个量级的工程。
2. **LLM 网关缺失**：直连模型 API，没有统一网关/路由/多模型 fallback/成本熔断的独立层（单任务预算熔断有，全局路由没有）。
3. **观测成熟度**：有结构化日志与落库事件，但没有 OpenTelemetry/trace UI/告警——「能查」到「能监控」差一步。
4. **连接器面窄**：Lago/Orb/CSV 三类，生产客户大概率要 Stripe/微信支付/支付宝/银行流水——每家约 1 天但没做。
5. **安全审计级**：SOC2/GDPR 级的审计与数据驻留方案没有做（金融/政企私有化部署时才需要，架构上预留了位）。
6. **真实流量校准**：意图路由的阈值（快路径字数、缓存 TTL、挂起时长）是拍的工程值，业界要求真实流量打标校准——自用流量还没积累到校准的量。

## 五、未来规划（技术层）

按价值排序，不是时间表：

**近期（顺手可做）**：
- **连接器扩充**：Stripe（订阅经济标杆）、微信支付/支付宝账单 CSV（国内交付立刻能用）——走现有 BillingConnector SPI，一家约 1 天。取数是价值链最上层，每加一家 = 一个可讲的故事。
- **LLM 网关层**：统一多模型路由 + 按成本/延迟 fallback + 全局成本熔断 + 单价快照对齐价格表——把「LLM 是增强不是依赖」从架构态度变成工程保证。

**中期（价值跃迁）**：
- **全库巡检长任务**：单 agent loop + 计划模式，自主跑全部规则 → 汇总 → 出周报。注意这是**单 agent 长任务**，不是多 agent——规划已在多 agent 取舍里钉死。
- **意图语义缓存向量版**：等 fallback 语料大到归一化压不住再上 embedding，复用知识层的键思想但换相似度检索；阈值按业界做法用真实流量校准。
- **观测升级**：OpenTelemetry 接入 + 归因/路由全链路 trace 回放 UI——把「每步落库」变成「可视化回放」。

**远期（形态变化，需先拍板）**：
- **多租户 C/S 化**：从单机工具变成可服务多客户的稽核服务——这是产品化分水岭，架构预留了位但工程量是另一个量级。
- **私有化部署包**：金融/政企数据不出域场景，含本地 LLM（vLLM/Ollama）+ 专属云方案。

**明确不做的**：多 agent 编排（理由见 2.6，重新评估的信号是「出现需要 agent 间自主协商的真实场景」）；把 LLM 引进金额计算（铁律，永不重开）。

## 六、一句话定位（收尾）

> recon-lens 是 agent 架构里的「确定性能力层」：核心对账零 LLM、可复现可审计，LLM 被钉在解释/翻译/起草三个位置且全部有降级兜底；它自带一套对齐业界 2026 共识栈的 agent 编排（快慢路由、证据三态、槽位状态机、评估闭环、golden 回归），但明确不做多 agent——编排交给外部 harness。架构按生产级标准建（1041 测试、降级矩阵、可回放、审批链），部署形态仍是单机原型；下一步的杠杆在连接器扩充与 LLM 网关，形态分水岭在多租户 C/S 化。
