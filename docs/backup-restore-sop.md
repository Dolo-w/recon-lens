# 备份与恢复 SOP（清单 P0-7）

> 这份文档的存在理由：**备份没演练过，等于没有备份**。
> 所以下面每一节都写"怎么做"和"怎么验证做到了"，而不是只写原则。

## 1. 目标（先定标尺，再谈手段）

| 指标 | 目标值 | 说明 |
|---|---|---|
| **RPO**（最多丢多少数据） | ≤ 24 小时 | 每日一次全量备份。要求更小就加 binlog 增量，那是另一套活 |
| **RTO**（多久能恢复服务） | ≤ 30 分钟 | 单库百 MB 级实测值；数据量涨上去要重测 |
| 备份保留 | 7 天（可配） | 生产建议 30 天 + 每月归档一份到冷存储 |
| 演练频率 | **每季度一次** | 只备份不演练，第一次真恢复就是事故现场 |

## 2. 日常备份

```bash
# 环境变量提供凭证（不要写在命令行里，ps 能看到）
export MYSQL_PASSWORD='...'

# 标准备份：默认保留 7 天，输出到 ./backups
./scripts/backup.sh

# 生产建议：放到独立磁盘/挂载点，保留 30 天
MYSQL_HOST=10.0.0.12 MYSQL_PASSWORD='...' BACKUP_DIR=/data/backups BACKUP_KEEP_DAYS=30 ./scripts/backup.sh
```

脚本做了四件事，每件都有对应的失败保护：

1. **`--single-transaction`**：InnoDB 一致性快照，不锁表 —— 备份期间业务照常跑。
2. **凭证走临时 `defaults-extra-file`**（umask 077 + trap 清理）：不出现在进程参数里。
3. **备份后立刻校验**：`gzip -t` + 统计 `CREATE TABLE` 条数，少于 5 张直接失败退出。
   **坏备份要被当场发现，而不是等恢复那天。**
4. **保留策略**：按 `-mtime` 清理，避免备份目录把磁盘吃满（这是真实发生过的故障）。

### 定时化（cron）

```cron
# 每天 02:30 备份，日志留一份
30 2 * * * cd /opt/recon-lens && MYSQL_PASSWORD='...' BACKUP_DIR=/data/backups \
  ./scripts/backup.sh >> /var/log/recon-backup.log 2>&1
```

**定时任务必须配告警**：备份脚本非 0 退出时应当触发告警（见 `docs/` 告警配置）。
"备份一直在失败但没人知道"比"没有备份"更危险，因为你以为有。

## 3. 恢复演练（每季度一次，务必按期做）

### 3.1 恢复到验证库（默认行为，安全）

```bash
export MYSQL_PASSWORD='...'
./scripts/restore.sh /data/backups/recon_lens-20261122-023000.sql.gz --yes
# 没给 --database 时会自动建 recon_restore_verify_<时间戳>，不碰任何已有库
```

### 3.2 业务级校验（自动校验替代不了这一步）

脚本只验证"表数量对不对"，业务正确性必须人工核对三件事：

1. **起一个实例连验证库**，打开 `/api/reports/finance?days=30`，数字与备份前一致；
2. **跑一次对账任务**，差异条数与备份前同一任务相符；
3. **抽查规则版本**：`recon_rule` 里的 `version` 与 `status` 分布合理（不该出现大量 DRAFT）。

## 4. 真事故恢复（覆盖生产库）

⚠️ **不要跳步。** 覆盖生产库是不可逆操作。

```bash
# 0) 先保住现场：把当前库也备一份（可能是逻辑损坏而非数据丢失，这份用于事后分析）
MYSQL_PASSWORD='...' BACKUP_DIR=/data/backups/incident ./scripts/backup.sh

# 1) 停应用（避免恢复过程中有写入）
#    docker compose stop recon / systemctl stop recon-lens

# 2) 恢复到生产库（必须显式给库名 + --yes）
MYSQL_PASSWORD='...' ./scripts/restore.sh /data/backups/recon_lens-<最近可用>.sql.gz \
  --database recon_lens --yes

# 3) 按 3.2 做业务校验，再启应用
```

### 恢复前必须想清楚的一件事

**RPO ≤ 24h 意味着最多丢一天数据。** 如果丢不起（例如账单已对外发出），
恢复后必须补跑这段时间的任务、并对账核对 —— 不要假设"恢复了就完事了"。

## 5. 已知边界（诚实列出）

- **只覆盖 MySQL**。H2 内存库是开发/演示用的，重灌即初始化，不适用这套流程。
- **没有 binlog 增量**。RPO 就是备份间隔。要更小需要额外的 binlog 归档方案，当前未实现。
- **大表恢复会慢**。百万行级 `recon_diff` 恢复时间未实测，数据量到那个量级要重做 RTO 评估。
- **脚本测试只验证"能跑"**（语法 + dry-run + 保护性参数在位），
  **真正的恢复演练必须在有 MySQL 的环境做**，见第 3 节。
  单元测试不假装自己验证了那件事。
- **备份文件本身没有加密**。含客户数据的部署，落盘前应加 `gpg`/`age` 加密，当前未内置。
