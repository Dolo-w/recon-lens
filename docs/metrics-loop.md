# 指标闭环（没有真实流量时怎么"上线"）

> 一句话：上线后的每一次坏结果（超时、否认、反复澄清、乱选工具），都必须能变成题库里的一道题，
> 48 小时内复现成红用例 —— 而不是靠人回忆。

## 一、为什么需要它

Agent 的三个失败面（模型判断、工具选择、叙述）都不在单元测试的射程内。
本项目的现实是：**没有真实用户流量**。所以闭环的"被测系统"是**评测批次**（`recon_eval_case` 表里的
一个 batch），流量来自：①金标 38 题（30 单轮 + 8 多轮）②故障注入 ③上线后的坏样本（人工补题）。

闭环不是"多跑几次评测"，而是**四个时间尺度各有一道闸**：

| 尺度 | 什么时候 | 闸 | 现状 |
|---|---|---|---|
| 改代码前 | 每次改动 | `mvnw test`（868 项，含闸门/预算/恢复/工具决策/起草收参） | 已有 |
| 合入前 | CI | `eval.yml`：p1（词表）+ p2（真模型）各跑一遍，退步即红 | 已有 |
| 每天 | 定时 | 同一份金标，看四个指标的趋势（不是看单次） | 待接调度 |
| 上线后 | 事故当天 | 坏样本入库为题目，次日必须能复现 | 机制已备（`/api/eval/*`） |

## 二、指标与旋钮

指标（`EvalMetrics`）：意图命中率（≥90%）、工具选择率（≥85%）、平均轮数（≤3，只看多轮题）、
每会话 token 中位数（≤6000）、p95 时延（观测）、通过率。

旋钮（改一个，看指标怎么动）：

| 旋钮 | 默认 | 抖动方向 |
|---|---|---|
| `recon.chat.loop.enabled` | false | 开：轮数 2.13→1.9、token ↑ 20% |
| `recon.chat.llm.timeout-ms` | 60000 | 降：平均时延 ↓、工具选择率 ↓ |
| `recon.chat.planner.keyword-accept` | 0.7 | 升：模型更少接管、意图命中率 ↓ |
| `recon.chat.summary.enabled` | true | 关：长会话 token 爆炸 |
| 温度 / 模型 | 固定 | deepseek-flash vs v4-pro |

### 2.1 决策式改造后，「工具选择率」怎么量（2026-10-28）

P2 改成模型直选工具后，**"意图命中"不再是可观测的决策**——它是工具名反推出来的副产品
（`ToolCallPlanner.intentFor`，映射不到就记 `HELP`）。所以两个指标要分开量：

| 指标 | 决策式下怎么算 | 为什么不能沿用旧口径 |
|---|---|---|
| 意图命中率 | `actual_intent == expected_intent` 仍然算，但**只当兼容指标**；`HELP` 不再等价于"没听懂"（模型可能已经用 `reply` 回答了） | 以前 `HELP` 一定意味着"要澄清/要菜单"；现在它也可能是"模型直接回答了一个问题" |
| 工具选择率 | 分母 = `expected_tool` 非空的题；分子 = 轨迹里**实际出现过的工具名**（`tool` 事件，含第二跳） | 以前分母是"被判定为需要工具的题"，判定本身就靠意图；现在直接看事件流，不经过意图 |
| 多轮完成度 | 不变：`multi=true` 上的平均轮数 | 与决策方式无关 |

**新增一条观测**：`budget` 事件（`turnTokens` / `tokensUsed` / `phase`）。
它回答"这轮吃了多少预算、在理解档还是执行档"——决策式下模型可能连问三轮才调工具，
token 涨在这三轮里；只看每会话中位数会把这段藏起来。

**口径提醒（2026-10-28 写动作统一之后）**：`byIntent` 按**执行轮次**记，写动作是两段式
（回执一轮 + 确认后执行一轮），所以一句「跑一下 BILL_VS_SETTLE」会让 `RUN` 计 **2**。
拿它算"意图命中率"时要把确认轮剔掉（那一轮没有新的用户意图，只是"点头"），
否则单轮意图题的命中率会被两段式稀释。工具选择率不受影响——它只看 `tool` 事件。

**起草收集轮也不进分母**（2026-10-28）：起草被模型点名之后，前几轮由收集器接管（问表/问列），
这些轮**不发模型请求**、也没有 `tool` 事件。它们看起来像"没有工具调用的对话轮"，实际是"还没到调工具的时候"——
统计时按 `plan` 事件有没有 `source` 区分：收集轮没有 `plan` 事件，直接排除。

**目前不设门禁**：决策式的工具选择率还没有基线（金标 38 题的期望工具是照旧口径标的），
先记数、看两批趋势，再定 SLO。见 `docs/open-questions.md` §四 M-c。

### 2.2 自由循环（`recon.chat.mode=loop`）要量的三件事（2026-10-28）

loop 模式下一次用户发言可能走 1–6 跳，每跳一次模型请求。"每会话 token 中位数"不够用了，
要拆成三条：

| 指标 | 怎么算 | 用途 |
|---|---|---|
| **跳数分布** | 每轮 `loopTurn` 的 `hop` 次数（日志 `自由循环结束 hops=N`；`logs/loop-probe-*.json` 的 `hops[]`） | 判断"要不要一次查两张表"这类行为是常态还是异常；跳数暴涨说明手册/工具描述没讲清 |
| **每轮 token** | `budget` 事件的 `turnTokens` | 和 legacy 同题对比：实测 loop 单轮更贵（3310 vs 2499 / 八句），但换来"不被半截状态绑住" |
| **参数一次正确率** | 写动作**第一次**发起时参数就齐（不需要回一句"还缺什么"）的比例 | 这是 loop 模式最该盯的指标：模型有没有先查列再写规则 |

配套提醒：

- 中间步骤不发 `tool` 事件也不会出现在给用户的文本里，但它们在 transcript 里——统计"这条链路用了哪些工具"
  要读 `plan` 事件序列，不能只读最终回复。
- 薄起草（`businessDescription` < 40 字）被打回那一跳**不算**参数错误，它还没到"发起写动作"：
  按 `plan` 事件里有没有 `tool=recon_draft_rule` 且有没有产生回执来区分。
- 切模式时 `pendingAction` 要清：legacy 的悬置回执和新模式混在一起，会让"确认"落到错误的动作上。


## 三、三道门（已实现）

1. **SLO 绝对门槛**：`GET /api/eval/{batch}/metrics` 返回四项口径与判定；CI 里有 `grep` 断言。
2. **退步门禁**：`golden-run.mjs` 带 `EVAL_BASELINE=<batch>` 时，与基线逐项比差，
   超过 `EVAL_MAX_REGRESSION`（默认 0，允许的退步百分点）即 `exit code = 1`。
   实测：拿一个"严格基线"（100/100/1 轮/1 token）比本批次 → 轮数 2.13、token 141，
   报 `[FAIL] 相对基准 strict-baseline 退步：平均轮数、token 中位数`，退出码 1。
3. **故障注入**：`work/fault-injection.ps1` 造三种故障（模型输出坏 JSON / 模型进程不可用 /
   起草拿到致命违规），契约是"降级而不是把异常抛给调用方"，产出 `docs/degradation-matrix.md`。
   实测 3/3 PASS。

## 四、一次真实的对口径（第一步的动机）

同一份金标、同一个应用，两套口径差了一倍：

| 指标 | 错的口径 | 对的口径 | 差在哪 |
|---|---|---|---|
| 平均轮数 | 1.24 | 2.13 | 把 30 条单轮题也算进"多轮平均" |
| token 中位数 | 265 | 151 | 把 chars 当 token，且多轮题只取末轮 |

教训：**指标口径本身要进代码并写清分母**（`EvalCase.multi` 就是为了这个）；
数字对不上时先怀疑口径，而不是先怀疑系统。

## 六、边界（这些事它做不到）

1. **题库是自己写的**：100% 不等于线上 100%，它只证明"改坏的能被当场发现"。
2. **桩模型只能测管道**：p2-stub 的分数不说明模型质量，只说明链路通。
3. **指标是代理**：意图命中 ≠ 用户满意；`passed` 依赖各题自带的判定器。
4. **单机**：评测与业务共库（`recon_eval_case` 和业务表在同一个 H2/MySQL），
   跑评测会占连接池；生产多实例时要拆库或加锁（本任务的边界）。
