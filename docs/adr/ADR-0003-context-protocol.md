# ADR-0003　上下文与指代解析协议

- **状态**：提议（Proposed）
- **日期**：2026-10-25
- **影响面**：`chat/`（`ChatRuntime`、`ChatSlots`、`chat/plan/`）、`web/`（SSE 事件字段不变）
- **补充关系**：不推翻 ADR-0001 的 **D2 / D7**（存储侧与压缩侧），只补它们没覆盖的**填充侧**
- **前置阅读**：ADR-0001 D2（短期记忆 = 结构化槽位）、D7（工具结果预算先于摘要）

---

## 0. 一句话

模型是无状态的：**它不记得上一轮，只觉得你这次发给它的字**。
所以上下文不是"喂历史给模型"，而是**在本机把事实存成结构，每轮只发最小、最稳的那一份**。

---

## 1. 背景：为什么现在每次都要打补丁

ADR-0001 规定了上下文**存在哪**（`recon_chat_turn` / `state_json` / `summary`）和**什么时候压**（窗口 55%），
但没规定**下一句话怎么变成槽位**。现实里这件事被拆成了六处各自实现：

| # | 决策点 | 代码位置 | 现状 |
|---|---|---|---|
| 1 | 这句话想干嘛 | `CompositePlanner` + `LlmPlanner` + `KeywordPlanner` | 模型优先理解；词表只保留零参数短问句快路径（2026-10-25 修正） |
| 2 | 这句是不是在回答上一问 | `ChatRuntime#resumePending` | 三个 `if`（起草 / 跑一次 / 看字段），每个新动作加一个 |
| 3 | 参数从哪来 | 各动作内 `firstNonNull(call.x(), slots.x(), …)` | 出现 5 次 |
| 4 | 缺参数怎么办 | `run` 反问；`jobSummary/listDiffs/explainJob` 用"最近一次任务"；`onlyRuleCode` 用"唯一规则" | 4 处 `latestJobId()` + 1 处 `onlyRuleCode()` |
| 5 | 用了槽位要不要说明 | `assumedJobNote` / "续接上一轮" / "已记下" | 只有任务号和续接有，其余没有 |
| 6 | 取消与裸词指代 | `CANCEL` / `CANDIDATE_REF` / `DraftIntake#matchColumn` | 散在 3 处正则 |

后果：**同一个问题在三处各判一次，口径还不一致**；加一个动作就要再抄一遍兜底；
出了 bug 也说不清是"没听懂"还是"听懂了但没填对"。

这不是实现懒，是**协议缺失**。本 ADR 补的就是这份协议。

---

## 2. 设计判据（从模型的实际行为反推）

模型的四个客观事实，直接决定协议形状：

| 事实 | 后果 | 设计动作 |
|---|---|---|
| **无状态**：服务端不记得上一轮 | 指代必须在本地解掉，或每轮重发 | 事实进槽位；历史只在必要时发 |
| **前缀缓存**：相同前缀复用 KV，命中便宜得多 | 前缀里放任何会话变量，缓存全失效 | prompt 分四层，**稳定在前、易变在后** |
| **注意力中间最弱**：对开头/结尾敏感 | 长历史会把关键事实埋掉 | 事实放结构化的焦点段；历史上限 6 条、每条 120 字 |
| **概率生成**：没有"我不确定"的内部信号 | 会给一个看起来合理的错答案 | 约束解码 + 白名单解析 + 词表兜底 + 唯一性法则 |
| **看不到你的库**：只认识 prompt 里的字 | 会编一个"听起来对"的规则名/任务号 | 每轮注入**系统事实卡片**（只有元数据），并用它**校验模型输出** |

> 最后一条尤其重要：模型给的 `confidence` 是它顺手写的数字，**不是校准概率**。
> 所以本协议**不用它做决策**，只当排序信号（沿用 `CompositePlanner` 现有做法）。

## 3. 核心模型：三层状态 + 一个解析器

### 3.1 三层状态（沿用 ADR-0001 的存储，不动表结构）

| 层 | 载体 | 语义 | 谁写 |
|---|---|---|---|
| **事实** `Fact` | `recon_chat_turn` | 逐轮原文，只增不改 | 每轮 append |
| **焦点** `Focus` | `state_json` → `ChatSlots` | "现在在说哪条规则/哪个任务/哪张表" | 解析器写回 |
| **挂起** `Pending` | `state_json` 内 `pendingAction/pendingArgs` | "有一个空在等用户填，且只等一个" | 反问时写，收齐清 |

`ChatSlots` 现状（本 ADR 只补语义，不加表）：

```json
{
  "ruleCode": "AUTO_BILL_LEFT_BILL_RIGHT",
  "jobId": 12,
  "diffId": null,
  "table": "bill_left",
  "lastIntent": "JOB_SUMMARY",
  "focusTypes": [],
  "pendingAction": "DEFINE_RULE",
  "pendingArgs": {"left": "bill_left", "hint": "订单和状态"}
}
```

### 3.2 一个解析器：`ContextResolver`

所有"这句话在指什么"只走它一次，动作层不许再判空：

```java
public interface ContextResolver {
    Resolution resolve(String message, ChatSlots slots, List<String> history);
}

public record Resolution(
        ChatIntent intent,
        Map<String, String> args,          // 已填好的参数
        Map<String, Source> provenance,    // 每个参数从哪来：EXPLICIT / PENDING / FOCUS / DEFAULT / MODEL
        IntentSource source,               // KEYWORD / LLM / PENDING
        double confidence,                 // 排序信号，不是概率
        String reason,                     // 给人看的一句依据
        Ask ask);                          // 非空 = 该反问

public record Ask(String question, ChatIntent action, Map<String, String> collected, List<String> candidates) {}
```

### 3.3 五步解析（顺序不可换）

```
resolve(message, slots):
  1. pending 消费      这句能不能填上 pendingArgs 的空？能 → 就地消费，不再判意图
  2. 意图判定          模型优先（带 pending 问题 + 焦点 + 有界历史）；只有「无挂起、零参数、≤12 字的读问句」走词表快路径
  3. 参数填充          显式 > pending > 焦点 > 唯一候选 > 动作自己的默认策略
  4. 决策              参数齐 → 执行；不齐 → 反问（写 pending，只问一个）
  5. 回执              凡是用 FOCUS/DEFAULT 补的，回复里必须说明依据
```

**为什么 pending 必须排在意图之前**：用户回「就这两个吧」「BILL_VS_SETTLE」「字段」时，
这些句子本身不构成动作（词表给 HELP），但它们**在回答上一个问题**。
先判意图就等于丢掉 pending，这正是上一轮 `就这两个吧` 掉进帮助的原因。

**为什么参数填充要记 `provenance`**：它是"为什么这个问了那个没问"的唯一解释来源，
也是回执文案与审计（B31 路由落表）的数据基础。

**2026-10-25 修正：意图判定改成模型优先。** 原来的顺序是「词表命中就执行，命中不了才问模型」，
实测的问题不是模型听不懂，而是模型**根本没被问**：'就这两张，用状态和订单对' 被词表判成
`DESCRIBE_TABLE`，'订单和状态' 直接丢掉；用户只能反复说，直到某一句恰好被词表认对。
词表认的是字面，理解的是人。现在的分层是：
- **理解层归模型**：这句话要干嘛、在回答哪一问、指的是哪张表/哪条规则/哪个任务；
- **事实层归代码**：列是否存在、规则编码是否存在、参数校验、审批票、归档——模型给的每个值都要过白名单；
- **放行层归人**：测算/生效前的软审批不变。
词表只剩两类用途：零参数零歧义的短读问句（「有哪些规则」）直接走快路径；模型不可用时整条链路降级。
代价是每轮多一次模型调用（约 1–2s），换来的是"先理解再执行"，而不是"先猜一个再擦屁股"。

### 3.4 唯一性法则（本 ADR 的核心约束）

> **省略只在候选唯一时合法；否则反问，并列出候选。**

| 场景 | 候选数 | 处理 |
|---|---|---|
| 「跑一下」而库里只有 1 条规则 | 1 | 可省略，直接用（回执注明） |
| 「跑一下」而库里有 4 条规则 | >1 | 反问 + 列候选，写 pending |
| 「字段」而已知 `table` | 1 | 直接用 `slots.table` |
| 「字段」而 `table` 未知 | 0 | 反问"看哪张表的字段？" + 候选表名 |
| 「就这两个吧」而上一句列了 2 张表 | 2（就是那两张） | 用候选顺序填 left/right |
| 「就这两个吧」而上一句列了 5 张表 | 5 | **必须反问**（当前实现会取前两张，属已知缺陷） |

这条法则一次性覆盖了"裸词/指代/省略"三类问题，不需要为每个说法写一段正则。

### 3.5 读写分策

| 类别 | 缺参数时 | 理由 |
|---|---|---|
| **读**（任务总览、差异、归因、看字段） | 可默认"最近一次 / 唯一候选"，**必须回执** | 猜错的代价是答非所问，用户看得到回执就能纠正 |
| **写**（跑一次、重跑、起草、建模型） | **必须显式**，不许默认 | 猜错的代价是改了数据，回执救不回来 |

这条把现在"run 问、jobSummary 不问"的差异**从巧合变成规则**。

### 3.6 回执规则

凡参数来自 `FOCUS/PENDING/DEFAULT`，回复首句必须带依据：

- `（按会话里的规则 BILL_VS_SETTLE 查）`
- `（没给任务号，按最近一次生产任务 #12 回答）`
- `（续接上一轮：还在建规则，左 bill_left）`

来自 `EXPLICIT` 的不回执——用户自己刚说的话，不需要复述。

### 3.7 事实校验与"证据等级"（替代置信度判断）

模型给的 `confidence` 没有校准，**不能拿来当概率做决策**。决策只看四档证据：

| 证据 | 含义 | 处置 |
|---|---|---|
| `EXACT` | 词表确定性命中 | 直接执行 |
| `CONSISTENT` | 模型给的参数都能在事实卡片里对上 | 执行 |
| `UNVERIFIED` | 对不上也没矛盾（没取到事实、或缺参数） | 读：执行 + 回执；写：问 |
| `CONFLICT` | 说了个库里不存在的规则/任务/表 | **不执行**，澄清 |

规则：

1. `CONFLICT` 一律澄清，哪怕模型给了 0.95 —— `把 NO_SUCH_RULE 过一遍账` 必须问，不能跑；
2. 事实卡片为空时**不校验**（空集合 ≠ 库里没有，见 §4.5）；
3. 写动作缺关键参数（`RUN` 缺 ruleCode、`RETRY` 缺 jobId）时，**先让模型拿事实补一次**，
   补不上再问用户——「跑一下那个账单对账」不该让用户自己报编码；
4. `confidence` 只出现在展示层（plan 事件的 `conf`），不参与任何分支判断。

### 3.8 澄清的形态

带候选的"没听懂"不等于"要说明书"：返回一句短问句 + 可点候选，**不要打印整页帮助**。

```
没太确定你指的是哪件事（你要跑的规则 NO_SUCH_RULE 不在系统事实的规则列表里）。
点下面的选项，或者说得更具体一点：
· 跑一次  · 看规则  · 定义规则
```

### 3.9 两段式：写操作先说一遍再动手

写动作（`RUN` / `RETRY` / `BUILD_MODEL` / 起草收齐后的 `DEFINE_RULE`）分两段：

```
第一段：我理解你要跑一次账单与结算的对账（BILL_VS_SETTLE），确认执行吗？
第二段：用户回「确认」→ 真的执行；回「取消」→ 丢弃；说别的 → 当新指令
```

判据不是"是不是写"，而是**参数是不是用户自己说出来的**：

| 用户这句话 | 处理 |
|---|---|
| 「跑一下 BILL_VS_SETTLE」（点名了编码） | 直接执行，不确认 |
| 「跑一下那个账单结算的对账」（靠事实推断） | 先确认 |
| 「就这两个吧」（靠候选推断） | 起草流程内部消化，收齐后再确认 |
| 缺关键参数（没说哪条规则） | 先反问，不确认（反问本身就是确认） |

实现要点：

- 确认句由模型生成（它能看到"用户原话"与"理解结果"的对照），**模型不可用则退回模板**——
  确认这一步是安全边界，不能因为模型挂了而消失；
- 待确认状态存 `pendingAction=CONFIRM` + `pendingArgs{intent, ruleCode, jobId, body, summary}`，
  下一句按"是 / 否 / 其他"三分支处理；
- 起草的确认消息里带**完整 YAML**——"给我完整展示"和"确认要不要落库"是同一个时刻；
- `DEFINE_RULE` 在参数没收齐时**不确认**：那时正该一句句问，不能让确认把收集流程掐断。

### 3.10 工件级上下文：草稿账本与归档

对话有上下文，**会话产出的规则版本也有上下文**。一个会话里起草三条规则时，"第二条"指谁、
哪一版被哪一版取代，都必须有事实依据，而不是靠模型记着。

**账本**（事实层，只增）：`recon_chat_draft(session_id, rule_code, rule_version, label)`

- 起草成功后写一行；`label` = 表名 + 维度 + 比对字段 + **用户原话**（`用户说：订单和状态，金额`）——
  规则体里是 `order_no`，用户嘴里是"订单"，两者都要能对上；
- `GET /api/chat/sessions/{id}/drafts` 返回带 `index` 的列表——"第几条"就是它；
- 引用解析优先级：**显式编码 > 焦点 > 第 N 条 > 描述匹配（表名权重 2、中文二元组权重 1，
  唯一最高分且 ≥2 才用）**，都不唯一就反问。

**命名**：起草收齐后由模型建议编码（`ORDER_STATUS_AMOUNT_RECON`），代码做
白名单正则 + 唯一性校验（撞名加 `_2`）。名字里没有信息，任何解析都救不回来——
`AUTO_BILL_LEFT_BILL_RIGHT_2` 这种名字，人分不清，模型也分不清。

**归档**（规则库状态机，不由模型触发）：某版生效时，同 code 下其他 `DRAFT`/`REVIEWING`
→ `SUPERSEDED` + `superseded_by`；**不删行**。归档是折叠，不是遗忘。

### 3.11 摘要的第二层：归纳只在截断之上叠加

截断版是三个不变量的载体（没有 key 可用、可复现、压缩不改审计）。所以归纳**不是替换截断**，
而是在它前面叠两段：

```
〔结论〕模型写：≤3 条已经定下来的事
〔未决〕模型写：0–2 条待确认的问题
<截断版：事实 / 坐标 / 被否决 / 索引>   代码生成
```

硬约束：

1. 模型只写这两段；id、坐标、〔被否决〕一律代码生成；
2. **校验器**：模型段里出现的规则编码/任务号必须在材料里出现过，否则整段丢弃（`SummaryEnricher.guard`）；
3. 超长按**行**截断（切在半句上比不切更糟），上限 300 字；
4. 没有 key / 模型失败 → 原样返回截断版，水位线照常推进。

> 顺带修掉两个老 bug：〔被否决〕原来在**整段回答**里找关键词，任何带"不能/失败/无法"的正常回答
> 都被记成"用户方案被否决"；摘要行原来取"第一个长度 ≤64 的行"，加人话总结后落在了分隔符
> 「—— 明细 ——」上。现在前者只看首行前 80 字，后者取第一行非空（超长截断）。

## 4. Prompt 组装协议（针对前缀缓存与注意力位置）

### 4.1 四层结构，稳定在前

```
┌─ P0 system（稳定，可缓存） ──────────────────────────┐
│ 角色 + 动作表（15 行）+ 输出 JSON 格式 + 三条禁令      │
│ ⚠ 不许出现：时间戳、会话 id、随机数、任何本轮变量       │
├─ P1 focus（半稳定，结构化，≤80 token）──────────────┤
│ ruleCode / jobId / diffId / table / lastIntent / pending │
├─ P2 history（条件携带，≤6 条 × 120 字）──────────────┤
│ 仅当本句含指代词或存在 pending 时才带；否则整段省略      │
├─ P3 user（易变）───────────────────────────────────┤
│ 当前这句话                                           │
└──────────────────────────────────────────────────┘
```

**规则**：任何会话变量都不许进 P0。现在 `LlmPlanner` 把焦点与历史拼在 system 里，
等于**每一轮都让前缀缓存失效**——这是纯成本，没有收益。

### 4.2 预算（按字符近似，中文 1 字 ≈ 1 token）

| 段 | 上限 | 超了怎么办 |
|---|---|---|
| P0 动作表 + 规则 | 900 | 动作表只留 名字/一句话；样例只留 1 个 |
| P1 焦点 | 80 | 本来就只有六个字段 |
| P2 历史 | 720 | 从旧往新砍，先砍最早 |
| P3 当前句 | 200 | 超长就不带历史 |
| **合计** | **≈1900** | 远低于窗口，压缩条件很少触发 |

### 4.3 什么不进 prompt

- **工具结果**：由 D7 截断（前 20 行 + 翻页出口），且只在"要解释结果"时才回灌；
- **摘要**（`summary`）：是给人读的（接手、复盘），**规划阶段不注入**——槽位比摘要准；
- **assistant 轮次**：规划只看用户原话，避免模型复述自己上一轮的错误。

### 4.4 指代词检测（决定 P2 带不带）

```
它|这|那|这些|那些|刚才|上次|之前|上面|这两个|这两张|还有吗|呢|再来一次
```

命中才带历史；不命中就省 700 token 且保前缀缓存。

### 4.5 系统事实卡片（唯一允许进 prompt 的库内信息）

模型看不到库，所以要么给它一份索引，要么它只能编。卡片内容**只有元数据**：

```
规则（3 条）：
- BILL_VS_SETTLE：账单与结算对账；左 bill_left、右 bill_right，比 amount，键 order_no
- CUSTOMER_STATUS_RECON：… 
可对账的表：bill_left、bill_right
最近任务：#12 BILL_VS_SETTLE SUCCESS 差异4；#11 …
（以上只是目录与状态；你没有数据行的访问权限，不要编造任何金额、行数或差异内容。）
```

| 约束 | 值 | 理由 |
|---|---|---|
| 规则条数 | ≤ 6 | 索引，不是全量 |
| 任务条数 | ≤ 4 | 够回答"最近跑过什么" |
| 表名 | ≤ 12 | 够挑表 |
| 数据行 | **0** | 业务秘密；且模型不需要看 137 条差异才能说"该看明细了" |
| 生成时机 | 每轮重建 | 源是内存里的规则目录 + 任务表，代价可忽略 |

**空集合的语义**：卡片构建失败时退化成 `EMPTY`，`knowsRules()=false`。
校验方必须先看这个标志——否则一次数据库抖动会把所有规则判成"不存在"。

**为什么放 P1 而不是 P0**：它会随规则/任务变化（比焦点稳定，比动作表不稳定）。
放在动作表之后、焦点之前，能让"动作表"那一段继续命中前缀缓存。

## 5. 动作元数据（`ActionSpec`）

把散落的兜底写成一张表，代码按表生成反问与回执：

| intent | 参数 | 缺参策略 | 反问 | 回执 |
|---|---|---|---|---|
| `RUN` | ruleCode | 必须显式；唯一规则可省 | 「跑哪条规则？」+候选 | 省了才回执 |
| `RETRY` | ruleCode, jobId | 必须显式 | 「重跑哪个任务？」 | 否 |
| `BUILD_MODEL` | ruleCode | 必须显式 | 「给哪条规则建模型？」 | 否 |
| `DEFINE_RULE` | left/right/key/compare | 逐项问，**一次一个** | 见 §3.4 | 「已记下：…」 |
| `JOB_SUMMARY` | jobId | 默认最近一次 | — | 「按 #12 回答」 |
| `LIST_DIFFS` | jobId, diffType | 默认最近一次 | — | 「按 #12 回答」 |
| `EXPLAIN_JOB` | jobId | 默认最近一次 | — | 「按 #12 回答」 |
| `EXPLAIN_DIFF` | diffId | 默认最近一次任务里的该条 | — | 是 |
| `DESCRIBE_TABLE` | table | 焦点 > 唯一候选 > 问 | 「看哪张表？」+候选 | 用焦点才回执 |
| `TRIAL_STATUS` | ruleCode | 焦点 > 唯一规则 > 问 | 「看哪条规则？」 | 用焦点才回执 |

表里没有的动作（`HELP`/`APPROVE`）不需要参数，直接进。

## 7. 迁移（不改行为，三步）

| 步骤 | 内容 | 验证 |
|---|---|---|
| **1. 收口** | 抽 `ContextResolver`；把 `firstNonNull`×5、`latestJobId`×4、`onlyRuleCode`、`resumePending` 三个 `if` 搬进去，行为一字不变 | 先写 §6 矩阵（含现有 18 项冒烟），改动前后全绿 |
| **2. 注册** | pending 消费从 `if` 链改成"动作注册自己能消费什么"（`PendingConsumer`） | 矩阵 + `p2-multiturn.ps1` |
| **3. 表驱动** | `ActionSpec` 落地，反问/回执/默认策略由表生成；`provenance` 进 SSE `plan` 事件 | 矩阵 + 页面回执展示 |

**4. prompt 分层**（可独立做，收益是缓存命中率）：
`LlmPlanner` 的 system 只保留 P0，焦点与历史改放 P1/P2；命中测试：同一会话连续 5 句，
第 2–5 句的 prompt 前缀应与第 1 句的前 900 token 完全一致。

## 8. 与既有决策的关系

| 既有 | 本 ADR 的态度 |
|---|---|
| ADR-0001 D2「指代解析走槽位，不走全量历史」 | **坚持**。P2 历史只做"候选生成"，最终参数必须落 `args`；历史上限 6×120 |
| ADR-0001 D2 压缩三条件（55% / ≥4 轮 / ≥2000） | **不动**。本设计把 prompt 压到 ≈1900 token，压缩更少触发 |
| ADR-0001 D7 工具结果先截断 | **不动**，并明确"工具结果不进规划 prompt" |
| `CompositePlanner` 的置信度阈值 | **不动**，仍是排序信号 |
| 现有偏离：`LlmPlanner` 的焦点/历史拼在 system 里 | **修正**（§4.1）：P0 只放稳定内容 |

### 不做的

- **不做向量检索做指代**：对账场景词表封闭，槽位比相似度准（ADR-0001 §3 备选 B）；
- **不做跨会话记忆**：`SessionRecallService` 已有，但那不是"上下文"，是"长期检索"；
- **不把摘要注入规划**：摘要给人读，槽位给程序用（D7 的"分开存"原则）；
- **不追多轮自主规划**：一次只解析一个动作，不做"一口气完成三件事"。

## 9. 风险

| 风险 | 对策 |
|---|---|
| 模型凭历史直接给参数，绕过槽位 | `provenance=MODEL` 的参数必须来自本句字面；与槽位冲突时以本句为准，并在回执里点名 |
| 反问过多让用户烦 | 唯一性法则只在"候选 >1"时反问；读操作默认最近一次并回执 |
| 矩阵测试跟不上实现 | 矩阵是**契约**：加动作必须加行，`ActionSpec` 表里没有行就编译不过（枚举穷举） |
| 前缀缓存收益不可测 | 先用日志记录 `promptChars` 与首段哈希，观察同一会话连续轮次是否稳定 |
